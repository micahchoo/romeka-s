# Brief: publish (the front door and the paperwork)

## Goal

Make this repository publishable. A stranger who lands on it should learn what Romeka S is, that it is a fork of
Omeka S under the same license, how to run it, and how to contribute, in that order, without opening the source.

## Scope

Worktree `romeka-s-wt/publish`, branch `s2/publish`. Write only `README.md`, `LICENSE`, `NOTICE`, `CONTRIBUTING.md`,
`SECURITY.md`, `CHANGELOG.md`, `AGENTS.md`, `.gitignore`, `.github/**` and `docs/**`.

## Context

- The product is **Romeka S**, a fork of [Omeka S](https://github.com/omeka/omeka-s). Upstream is GPL-3.0 and this
  fork carries the same license, so `LICENSE` is the GPL-3 text verbatim, and `NOTICE` records the provenance: the
  upstream project, its license, the commit this fork was taken from (`5e413f009c447f4b587803ab23a9cec7d228f6e8`),
  and that the Rust core and the TypeScript admin are a reimplementation that keeps the upstream data model and API
  compatible.
- The data model and the API stay compatible on purpose: the `o:` JSON-LD prefix, the `/api` surface, the member
  names and the schema. That compatibility is a feature to state plainly, because it means an Omeka S client and an
  Omeka S database both keep working.
- `docs/` already holds a user guide, an operator guide, an API reference (`api.md`, generated by `docs/gen.sh`,
  never edited by hand), a compatibility note and a contributing guide. Keep the set, re-point the framing at the
  product, and drop anything that only made sense while porting.
- `.github/workflows/verify.yml` runs the port's fidelity gate, which needs the upstream clone, an oracle container
  and `verification/`, none of which live in this repository. Replace it with the product's own CI: fmt, clippy, the
  workspace tests, the SPA typecheck, lint, unit tests, build and the browser suite. Add a container build job that
  proves the image builds, and cache the Rust and npm dependencies.
- The repository is a fresh history with one import commit. The changelog starts there.

## Deliverables

- `README.md`: what it is, the provenance line, a quick start that works from a clean checkout, the deploy pointer,
  what is ported and what is not (the excluded surface, honestly), the speed claim with its numbers, and the
  license. Keep it under 200 lines; link out rather than inline.
- `LICENSE` (GPL-3 verbatim) and `NOTICE` (provenance and attribution).
- `CONTRIBUTING.md`, `SECURITY.md` (how to report a vulnerability, and what the session and the API key protect),
  `CHANGELOG.md` (the import commit and the account flows as the first entries).
- `AGENTS.md`: the rules an agent working in this repository follows. Adapt the port's version: the crates, the
  ownership rule, the private cargo target dir convention, the commit format, the report format. Drop the port's
  verification-harness rules, which do not apply here.
- `.github/workflows/ci.yml` replacing `verify.yml`, and `.gitignore` reviewed for a Rust and Node repository.
- `docs/**` re-framed for the product, with the compatibility note kept and sharpened, and the operator guide
  pointing at `deploy/DEPLOY.md` for production.

## Acceptance

- The CI workflow's every step is a command you ran locally, and you say which ones you ran.
- `cd web/admin && npm run typecheck && npm run lint && npm test && npm run build` green, and `cargo test --workspace`
  green, so the commands the README gives are real.
- Report the README's structure, the CI jobs, and anything you could not verify.

## Verify

- `cargo test --workspace` and `cd web/admin && npm ci && npm run typecheck && npm run lint && npm test && npm run build`

## Forbidden

`crates/**`, `web/**`, `packaging/**`, `deploy/**`, `Cargo.lock`.

## Timebox

4 hours. The README and the license first, then the CI, then the docs re-framing.

## Report

Per the repository's AGENTS.md.
